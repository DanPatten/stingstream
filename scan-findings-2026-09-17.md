## F1. `bun run typecheck` fails on a clean master, and CI cannot see it — **verified**

**Severity: high.** This blocks the documented local gate for everyone, and the reason CI is green
is that CI is checking less than you are.

```
components/DownloadItem.tsx(197,7): error TS2590:
  Expression produces a union type that is too complex to represent.
```

Reproduced twice, including immediately after `tools\dev.ps1` regenerated the route types, so it is
deterministic and not a stale-cache artifact. The tree was clean (`git status` empty) and
`DownloadItem.tsx` was last touched several commits back, so this is master's own state.

### Why CI is green and you are red

`apps/stingstream/tsconfig.json` includes `.expo/types/**/*.ts`, and `.expo/` is **gitignored**
(`apps/stingstream/.gitignore`). That file is generated by `expo export` / `expo start`, so:

- **locally** it exists, and `Href` resolves to the real generated route union;
- **in CI** (`.github/workflows/app.yml` → `checks` → `bun run typecheck`) nothing generates it, so
  the union never exists and TS2590 cannot fire.

So the `App / checks` job has been passing this file while the local gate rejects it. Any type error
that depends on real route types is invisible to CI today.

### Why the union is too complex

The generated `.expo/types/router.d.ts` is **120 KB** and contains **511** route literals, of which
**320 are not routes at all** — the typed-routes generator is walking files outside `app/`:

```
`/../components/cards/posterSize`
`/../components/cards/posterSize.test`
`/../assets/brand/wordmarkContrast.test`
`/../constants/Requests`
`/../utils/identity/verifier.test`
```

Test files and plain modules are being emitted as navigable routes. `app.json:209` sets
`experiments.typedRoutes: true`; there is no `EXPO_ROUTER_APP_ROOT` or equivalent override anywhere
in `app.config.ts`, `app.json`, `metro.config.js`, `babel.config.js` or the env files.

The offending expression is the `Href`-typed ternary at `components/DownloadItem.tsx:196-207`.

### Suggested order of attack

1. Fix the generator's root so only `app/**` produces routes — that alone drops the union by ~63%
   and very likely clears the error.
2. Make CI generate `.expo/types` before `bun run typecheck`, otherwise this class of error keeps
   shipping.
3. Independently, narrow the `DownloadItem.tsx:196` expression so it does not build a full `Href`
   union.

## F2. Settings → Logs & status is permanently broken once the side door switches origin — **verified, reproduced in the browser**

**Severity: high.** A whole settings pane fails, every time, in the configuration this node is
actually in.

### What happens

Loading the app at `http://127.0.0.1:5173` and opening **Settings → Logs & status → Status** shows
loading skeletons, then settles on:

> **Something went wrong**
> Failed to fetch
> Try again

It never recovers. Screenshots: `.playwright-mcp/06-diagnostics.png` (skeletons),
`.playwright-mcp/07-diagnostics-stuck.png` (final error state).

### Root cause

`apps/stingstream/lib/stingstream/status.ts:23-39`:

```ts
export function useHealthz() {
  const nodeBaseUrl = useNodeBaseUrl();
  return useQuery({
    queryFn: async () => { const res = await fetch(`${nodeBaseUrl}/healthz`); ... },
    refetchInterval: 5000,
  });
}
```

`nodeBaseUrl` is not the origin the page was served from. `ServerUrlProvider` races the side-door
candidates and switches the session to the owner's public address — in this environment
`https://meals.danha.top`. Confirmed in the network log: after the race, every app request goes to
that host.

`/healthz` is then a **cross-origin** fetch, and the gateway deliberately does not send CORS headers
on it. Confirmed directly against the local node:

```
/healthz                                status=200 ACAO=<none>
/stingstream/api/v1/mesh/status         status=401 ACAO=*
/stingstream/api/v1/qualityprofiles     status=401 ACAO=*
```

This is by design, and the design is written down in two places:

- `mesh/crates/stingstream/src/gateway/mod.rs:334-338` — `/healthz` "carries child ports, the data
  directory and the whole side-door state", so it must not be readable by any page on the internet.
- `apps/stingstream/lib/stingstream/sidedoor.ts:20-26` — a section literally headed
  *"Why `/sidedoor/v1/hello` and not `/healthz`"*.

So `useHealthz()` breaks a rule its own sibling module documents. `/sidedoor/v1/hello` is the
CORS-safe endpoint that exists for exactly this, and it answers 200 for this node (network log
request #31).

### Blast radius

`useHealthz()` has six consumers, all affected whenever the session is on the public address:

- `components/stingstream/node/NodeStatusScreen.tsx:143` (the pane above)
- `components/stingstream/downloads/DownloadsScreen.tsx:72`
- `components/stingstream/domains/ManualDomainDialog.tsx:82`
- `lib/stingstream/libraries.ts:75`, `lib/stingstream/downloading.ts:62`, `lib/stingstream/hooks.ts:39`

With `refetchInterval: 5000` and React Query's default 3 retries, this also fires **~4 failed
cross-origin requests every 5 seconds forever**, which is most of the console noise below.

## F3. Error copy on that screen breaks the project's own voice rules — **verified**

**Severity: medium** (rule violation, user-facing).

`components/stingstream/shared/ScreenState.tsx:52-80` renders `t("common.something_went_wrong")`
followed by the raw exception `{message}`, which is how **"Failed to fetch"** — a browser-internal
`TypeError` string — reaches the screen.

Both halves are explicitly ruled out in the root `CLAUDE.md`, "The voice of user-facing copy":

- *"'Something went wrong' when the actual problem is known"* is listed under tells to cut on sight.
- *"Errors say what failed, then the one thing to do."*
- *"never explain the system"* — `Failed to fetch` explains nothing to a reader.

The correct component already exists twelve lines further down: `UnavailableState`
(`ScreenState.tsx:104-141`), whose own docblock says *"Saying 'Something went wrong' for a server
that is simply off is a small lie that sends the reader looking in the wrong place."* A network-layer
`TypeError` is precisely that case and should route to `UnavailableState`, not `ErrorState`.

## F5. Mesh: a holder's response headers are trusted as a real file size — **verified by reading the code**

**Severity: high.** One malicious or buggy group member can exhaust the reading node's memory on any
playback.

`mesh/crates/stingstream-mesh/src/node.rs:3641-3667` (`span_of`) parses `start` / `end` / `total`
straight out of a peer's `Content-Range` with no clamp:

```rust
if let (Ok(start), Ok(end)) = (a.trim().parse::<u64>(), b.trim().parse::<u64>()) {
    return (start, Some(end), total.trim().parse::<u64>().ok());
}
```

`node.rs:2001-2016` feeds that straight into the chunker, and `swarm.rs:74-95` loops the whole span:

```rust
let mut at = start;
while at <= end {
    out.push(Chunk { index: out.len(), start: at, end: stop });
    ...
}
```

`Vec` has no cap and the loop is fully synchronous inside `async fn stream`.

**Failure:** a group member answers a range request with
`Content-Range: bytes 0-18446744073709551614/…`. `worth_swarming` (`swarm.rs:109-111`) only requires
the span to be ≥ `swarm_min_span_bytes`, which a span of `u64::MAX` trivially passes, so the chunker
runs and pushes 24-byte `Chunk` structs until the allocator gives up — while pinning a tokio worker.

Note the author already guarded the *arithmetic* overflow (`if stop == u64::MAX { break; }` at
`swarm.rs:89`) but not the vector's size. A sanity clamp on `end` against the known item size, or a
cap on `chunks()`' output length, closes it.

## F6. Mesh: peer-supplied node ids are stored unvalidated and then byte-sliced — **verified by reading the code**

**Severity: medium–high** (panic / DoS; exploitability depends on group membership).

`mesh/crates/stingstream-mesh/src/gossip.rs:885-889`:

```rust
Body::Membership { members } => {
    for m in members {
        let _ = db.note_member(group, &m.node, &m.server_name);
    }
}
```

`m.node` is an attacker-chosen `String`. No format check, no length check, no cap on
`members.len()`, and the `Result` is discarded.

`mesh/crates/stingstream-mesh/src/node.rs:3671-3673`:

```rust
fn short(node: &str) -> &str { &node[..node.len().min(12)] }
```

This is a **byte** slice. Any stored id whose byte 12 is not a UTF-8 char boundary panics the node
when it is logged. `short()` is called at `node.rs:1324`, `1328`, `2613`, `2649`, `3268` — the 1324
path is group-secret rotation, so a poisoned member list takes down the rotating node.

Two fixes, both worth doing: validate `m.node` on ingest (it should be a fixed-length z-base-32 id),
and make `short()` use `char_indices()` so it cannot panic on any input.

## F9. Console noise in a normal session — **verified**

Measured on node 1 with the tree as of this scan.

- **`/healthz` CORS failures** — the F2 loop. ~4 failed requests per 5 s, forever.
- **`/stingstream/api/v1/qualityprofiles` → 503, retried.** Seen 4× on a single item-page load
  (network log entries 127, 192, 194, 196). 503 here means the child that answers it is not running;
  retrying a structurally unavailable endpoint just multiplies the noise. Worth a `retry: false` or a
  503-aware retry predicate.
- **`useNativeDriver` warning on web.** `Animated: 'useNativeDriver' is not supported because the
  native animated module is missing. Falling back to JS-based animation.` Fires on navigation. It is
  a real perf note on web, not just noise — that animation is running on the JS thread.

A clean load of Home produces **0** console errors, so the above are the whole list.

1. **F1** — the local typecheck gate is red on master, and CI is structurally unable to catch this
   class of error. Fix the route-type generation first; it likely fixes both halves.
2. **F2 / F3** — a settings pane that always fails, with copy that breaks the house rules while
   failing. Point `useHealthz` at `/sidedoor/v1/hello`, and route network `TypeError`s to
   `UnavailableState`.

   console error.
